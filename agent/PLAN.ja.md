# 計画書：mechanism-agent v0.2–v0.5
## Swarm 式協働 + 会話タスク分岐 UI + Docker サーバー配置

- 状態：計画（未着手）。ベースライン：`agent/` v0.1（公開済み、コミット 79c3e100）。
- ベンチマーク：Google Antigravity の `/swarm`（名前つきエージェントチーム + 共有メッセージボード + 検証者）、
  および Claude Code 式の会話（メンバーごとに一本の会話ライン、分岐可能、チェックポイントへ巻き戻し可能）。
- 制約は不変：仕組みと内容の分離。クローズの三態、作者は自分を審査しない、スナップショットをリポジトリへ戻す等、v0.1 の
  強制ルールはすべて保持する。新機能はその上にだけ生やすことができ、迂回はできない。

---

## 1. 結論先行（実現可能性）

**実現可能。** v0.1 の核（認領ボード = 公共台帳、コーディネーター、作業/審査の分離、スナップショット）は
まさに Swarm の骨格である。Antigravity の coordinator による課題分割、名前つき worker、
公開 brief、共有 board、verifier の審査は、本仕組みのリーフ分割、認領、交付ブロック、
審査によるクローズと一対一に対応する。主に欠けているのは三層：**イベント/メンション層**（board を状態ログから
メッセージバスへ格上げする）、**メンバーのライフサイクル**（睡眠/起床/一時停止/退場）、
**サーバーと UI**（リアルタイム配信、会話ツリーと分岐）。本当に難しいのは二箇所だけ：
並行書き込みに耐えるストレージのインターフェース化と、分岐のデータモデル——第 5 節で選択を示す：
**会話は分岐してよいが、台帳は分岐してはならない。**

## 3. UI：Claude Code 式の会話とタスク分岐

- **メンバーごとに一本の会話ライン**：メンバーの全往来（brief、質問、交付、審査意見）は
  一本の読める会話であり、Claude Code のセッションのように上から下へ読む。ログに散らばらせない。
- **タスクツリーはそのまま分岐ツリー**：リーフの細分化（分割クローズ）は自然に分岐である——親リーフが閉じ、
  子リーフがそれぞれ会話ラインを開く。UI は「誰が誰から分かれたか」をツリー/グラフで示す。
- **分岐（fork）**：ユーザーまたはコーディネーターは、任意の会話の任意のメッセージで分岐できる：
  新しい会話はその接頭辞を起点に、別のやり方で続ける（例：モデルを替えてやり直す、角度を替えて問い直す）。
  分岐は新しいラインであり、旧ラインはそのまま残る——**歴史の書き換えは禁止**。台帳の追記式と一致する。
- **チェックポイントと巻き戻し（rewind）**：交付/クローズのたびに会話上にチェックポイントができる。
  巻き戻し = チェックポイントから新しいラインを分岐させることであり、時間を遡って記録を消すことではない。
- **人の位置**：UI の第一画面は引き続き「要決定」キュー（v0.1 のボードで確定済み）。
  会話と分岐は第二層で、任意のメンバー/任意のリーフをクリックして入る。

## 4. サーバーアーキテクチャ（Docker 配置）

単機一台のサーバーで、docker compose が一式を起動する。イントラネット配置は外部サービスに依存しない
（モデルエンドポイントを除く。それもイントラネット内のモデルを指せる）。

```yaml
services:
  server:      # API + コーディネーター：board/チケットの唯一の書き手、SSE でリアルタイムストリームを配信
  worker:      # ステートレスな作業/審査エージェントプロセス、複数レプリカに scale 可能。認領のみで、DB へ直接書かない
  web:         # UI の静的リソース + リバースプロキシ（Board/Members/Graph/会話ツリー）
  db:          # Postgres：board イベント、会話、チケット（第 5 節のストレージ階層を参照）
  gitea:       # 任意：人間規模のチケットとコードホスティング（docs/07 の形態）、または内蔵チケットを使う
volumes:
  state:       # スナップショットとエクスポート物。定時にスナップショットを git リポジトリへコミットして戻す（バックアップ規律は不変）
```

- **言語は一本に保つ**：サーバーは引き続き Python（標準ライブラリ → 軽量フレームワーク FastAPI）、
  UI はビルドステップなしのフロントエンド（素の JS + SSE）とし、イントラネット配置にビルドチェーンを持ち込まない。
- **リアルタイム**：サーバー → ブラウザは SSE（単方向配信で十分：board ストリーム、メンバー状態）。
  ブラウザ → サーバーの操作（仕事の割当、直通メッセージ、承認）は通常の POST で行う。
- **唯一の書き手**：すべての書き込みは server の API 検証を通る（v0.1 の board ルールをそのままサーバー側へ移す：
  クローズの三態、作者は自分のものを閉じられない、必須フィールドはサーバー側で遮断）。
  worker プロセスに直接書き込み権限はない——M1157 式の「書いてボードを壊す」はアーキテクチャ上あり得なくなる。

## 5. データモデルと二つの硬い選択

1. **会話は分岐してよいが、台帳は分岐してはならない。** board のイベントストリームはチーム全体で唯一の事実の
   系列であり、分岐は会話とワークスペースの層でのみ起こる：分岐した新しいラインは同じ台帳を読み、
   交付は引き続き同じ審査経路を通る。台帳の分岐を許せば、二つのラインがそれぞれ「検証済み結論」を
   育ててしまい、証拠体系はその場で失効する——これが本計画と一般的なマルチエージェントフレームワークとの
   最も重要な違いである。明文化し、議論の余地なしとする。
2. **ストレージの階層化**：v0.1 の JSONL は**エクスポート/スナップショット形式**として残す（監査とバックアップ）。
   サーバーのランタイム状態は Postgres に入れる（並行性とクエリに必要）。両者は server による単方向
   エクスポートでつなぐ：DB がランタイムの真源、スナップショットはバックアップと起動時の読み物——docs/07 の
   「チケット + スナップショット」と同じ規律を、全状態へ拡張したもの。

## 7. リスクと未決事項

- **並行性の正しさ**：複数 worker が同時に認領/クローズする競合は、サーバー側での書き込み直列化
  + リース（v0.1 に既にリースの意味論あり）で解決する。v0.2 では先に並行ストレステストを出してから量を増やす。
- **コンテキストコスト**：Swarm 式の公開 board は各メンバーにボード全体を読ませる——大きなボードには
  フィルタ付きビュー（自分に関係するものだけ読む）が必須で、さもないと token コストは人数の二乗で増える。Antigravity は
  「睡眠 + メンション起床」でこれを抑える。本文もこれに倣い、「メンバーは既定で自分へのメンションのある post だけを購読する」を加える。
- **ユーザーの決定待ち**：UI のログイン/権限の強さ（イントラネットの最小配置ではまずネットワーク分離に頼れるが、
  UI 自体は対話可能でなければならない。決定済み④を参照）。
- **決定済み（2026-11-15、ユーザー）**：②チケットは**外付け tracker（Gitea で可）**を使う。
  アーキテクチャ上は TrackerAdapter インターフェースとする：Gitea が最初のアダプタ。社内に既にローカルの
  GitLab がある場合は GitLab アダプタを使う（同じインターフェース、issues/MR/CI が一体、MR 承認が
  自然に「作者は自分を審査しない」に対応する）。接続方式は確定：**サーバーが REST API を呼ぶ**
  （token は server にだけ置き、エージェントは直結しない）。**MCP は不要**——外部の
  対話シェル型エージェント（Claude Code 類のツール）が同じ tracker を操作する場合にだけ追加する。
  **skill は必要**：チケット/MR/クローズの規律は `tracker-workflow` としてバンドル済み。
  ④**UI は必需品であり、対話可能でなければならない**（ユーザーがシステムと対話するため）：仕事の割当、直通メッセージ、
  承認、分岐はすべて UI から発するが、書き込みはすべて server の API 検証を通る——
  v0.1 ボードの「読み取り専用」はデモ形態にすぎず、v0.3 から UI は正式な操作面となり、
  唯一の書き手は引き続き server である。
- **決定済み（2026-11-15、ユーザー）**：③主シナリオは**数学研究**に定める。デモ課題とチェッカー
  エコシステムは研究課題に合わせる：命題の提示、証明の試み、反例探索、既知答えの記号/数値
  再計算。チェッカー登録表は証明チェック（形式検証インターフェース）と記号計算の方向へ拡張する。
  コード課題は副シナリオに格下げする。それに応じて、v0.5 の per-worker コードワークスペース（worktree）の
  優先度を下げ、会話分岐（証明の試みの別経路）の優先度を上げる——数学では
  「別のやり方でもう一度試す」が主需要であり、「複数人が同じファイルを編集する」ことではない。

## 8. 既存文書との関係

本計画は docs/01–07 のルールを一切変更しない。実装するのは docs/02（アーキテクチャ）を
サーバー形態へ拡大したものである。一期が着地するごとに、CHANGELOG に一版記録する。
ある期の検収が否決されれば、計画書はその場で改版し、旧版の記録を残す——計画自体も
本フレームワークの証拠規律に従う。
