# トラッカー・ワークフロー

チケットは人間スケールの層であり、リーフは機械スケールの層である。トラッカー（Gitea または GitLab、セルフホスト）はチケットとマージリクエストを保持し、ボードはリーフを保持する。どちらも他方を置き換えない。

## 対応関係

- **リーフのバッチ1つ ↔ チケット1つ。** チケットは人間スケールのタスクを述べ、それに分解されるリーフは参照フィールドにチケットの番号を持つ。チケットを閉じるには、すべての子リーフが閉じている必要がある——トラッカーのワークフローは、子が開いているチケットを閉じることを禁じ、スナップショットが違反を表示する。
- **ファイルを変更する交付物は、マージリクエストとして届く。** MR の説明文が、そのまま交付ブロックである（何が変わったか、どの数字か、チェッカーをどう走らせたか）。レビューは MR 上で行われる。著者は自分の MR を決して承認もマージもしない——これは礼儀ではなく、トラッカーの承認ルールが強制する。
- **質問と決定は issue である**。`question` または `decision` のラベルを付け、決定者をフィールドに名前で記す。決定文を逐語的に引用して閉じられるまで、決定キューに現れ続ける。

## 接続ルール

- トラッカーの API トークンを持つのは **server** だけである。ワーカーとレビュアーはトラッカーを直接呼ばない。server を通じて行動し、server がすべての書き込みをボードのルール（3つの結果のみ、自己クローズ禁止、必須フィールド）に対して検証する。
- システム自体に MCP は**不要**である：server はトラッカーの REST API を使う。MCP サーバーを追加するのは、*外部の*チャットハーネス型エージェントが同じトラッカーを操作しなければならないときに限る。このスキルの規律は、その場合にも拘束するよう書かれている。
- すべてのトラッカー書き込みは、次のサイクルでスナップショット・エクスポートに反映される。トラッカーとスナップショットが食い違う場合、セッションが起動時に読むのはスナップショットであり、その食い違いは黙って糊塗するものではなく、報告すべき欠陥である。

## クローズの規律

- クローズ理由は、該当する場合はボードの語彙（proven / refuted / split）を再利用し、通常のタスクには `done` / `dropped` を加える。ドロップされたチケットは、その理由をチケットの中に永遠に述べる。
- 次回トリガー日を過ぎても動きのないチケットは、自動的に日次ページへエスカレーションされる。沈黙は、システムが表面化させる状態であって、仕事が消える方法では決してない。
