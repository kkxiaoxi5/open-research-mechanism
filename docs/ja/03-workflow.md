# 03 · ワークフロー：命題から受領まで

## 概要

```
命題（事前予測付き） → 小リーフに分割 → クレームボードで申込 → 実行 → 提出ブロック付きで提出
      → 独立審査（再計算／ブラインド読み戻し／変異テスト） → 受付口で登記 → 変わった判断を毎日の一ページに書く
```

## 命題と事前予測

- 各命題は着手前に明記する：何に答えるのか、予測は何か（数量級付き）、どの結果が証明となり、どの結果が反証となるか、検出力は足りるか（`04-evidence.md` 参照）。
- 予測は結果を見る**前に**提出しなければならない（版管理の履歴のタイムスタンプが証人となる）。
- 検出力の不足する命題は、探索、誤りの調査、記録はできるが、確認や否定として書き上げてはならない。

## 小リーフへの分割（並列化の鍵）

- 大きな課題を、**機械判定を自ら備えた小さい問い（小リーフ）**に分割する：各ピースに明確な入力、明確な産出物、明確な自動判定基準（既知答え／単体テスト／ビット単位の再現）を持たせ、全体の課題に詳しくない実行者でも独立に完遂できるようにする。
- 小リーフは「人を増やせば加速する」の担い手である：派遣時刻を記録し、提出と検収の時刻はチャネルのメッセージを基準とする——このタイムスタンプ群こそが、拡張効果の測定値である。
- 分割の原則：判定類のツールを厚くしていくよりも、**表象と推論の類（甲類）**の小リーフを優先して切り出す。

## クレームボード（申込ボード）

タスク状態の最小の構造化された担い手（参考実装は `../reference/claimboard.py`）：

- **追記のみ**のイベントログ（JSONL）。証拠台帳と同じロックを共有し、並行書き込みで壊れないようにする。
- イベント種別：`open`（出題）、`claim`（申込）、`deliver`（提出）、`accept`（受入）、`reject`（差戻し）、`split`（分割）、`note`（備考）。
- 出題時の必須項目：出所（命題番号）、事前予測、検収方法。
- 提出時の必須項目：結果、および**それによってどの判断が変わったか**。
- **結末は三値のみ**：証明／反証／分割。「判定できない」で閉じることは拒否される。本当に詰まった場合は、詰まり点を三文以内で説明しなければならず、別角度の子課題が自動生成される。「待つしかない」タスクには別角度の子課題を必ずぶら下げ、空待ちは許されない。

## 提出ブロック

すべての成果物は冒頭に固定の五段を置く（テンプレートは `../templates/delivery-block.md`）：
タスクと仕様の版／結論／証拠状態（層別に表示）／成果物のパスと再現コマンド／残された不足と次の受領者。

## 審査

- 審査者は作者以外から指名する。一人の審査者が同時に審査する件数は 2 件まで（滞留を「審査中」に見せかけないため）。
- 三つの審査手段を必要に応じて組み合わせる：
  - **独立再計算**：別の人（または別のモデル）が原始入力から再計算し、ビット単位または許容差内で一致させる。
  - **ブラインド読み戻し／問い照合**：課題と原話だけを見て、成果物が実際に問われた問いに答えているかを照合する（「問われたことと違うことに答える」の防止）。
  - **変異テスト**：成果物の一か所をわざと壊し、テストスイートが捕捉できるかを見る。捕捉できない割合がテスト強度の実際の読みである。
- 審査結論は等級化する：受入／条件付き受入（条件を明記）／差戻し（不足項目を明記）。条件がすべて閉じるまで、成果物を下流で確認済みとして引用してはならない。

## 締めくくり

- 一つの課題を締めくくる条件は事前に書き明かす（例：主診断が走り終えて受け入れられた、訂正ページが確認された、締めくくりページが受け入れられた）。
- 締めくくりページには正直に書かなければならない：**何に答え、何に答えていないか**、前方記録で今後何を記録するか、保守者は誰か、再開条件は何か。
- 締めくくり ≠ 課題の否定。答えていない部分は「答えていない」と書き、「除外済み」とは書かない。
- 締めくくり後は、その課題は保守作業のみを残し、再開条件が発動しない限り、メインラインの研究時間を占有しない。
