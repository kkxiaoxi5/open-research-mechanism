# 07 · チケットとスナップショット：人間規模の仕事はトラッカーへ、状態はスナップショットでリポジトリへ戻す

複数セッションの協働が回り始めると、タスク、質問、決定といった**人間規模**の仕事（数十件のオーダー）は、Markdown の表をすぐに押し潰す：状態は手写しに頼り、閉単は誰かが思い出すことに頼り、「何が誰待ちか」は全文を通読しなければ分からない。本章の方案は：**この種の仕事を、ローカルにデプロイしたオープンソースの issue トラッカーへ移す。トラッカーの状態は定期的にスナップショットファイルとしてリポジトリへ書き戻す。** 機械規模の仕事（一括生成されるマイクロタスク）はトラッカーに入れず、付録式の追記台帳に残す（`03-workflow.md` のクレームボードを参照）。

## なぜ既成のトラッカーを使い、表を手作りし続けないのか

- 表にはフィールド制約がない：担当者、期限、次の引き金は、欄が丸ごと空のまま保存できてしまう。漏れと忘れはまさにこうして起きる。トラッカーの必須フィールドと状態機械は、**書き込みの時点で**遮断する。
- 表には通知がない：状態の変化は、誰かがたまたま読むことに頼る。トラッカーの割当て、ウォッチ、期限リマインダーは、「受領漏れ」を運の問題からシステムの問題に変える。
- 表にはクエリがない：「未回答の質問」「誰かの決定待ちの事項」「期限切れの仕事」は、保存済みクエリでワンクリックで表になるべきもので、毎回人が通読してまとめ直すものではない。
- 手作りの表の本質は、トラッカーの低品質な書き直しである——トラッカーは二十年かけて、漏れ、忘れ、履歴なしというこの三つを解決してきた。

## なぜスナップショットが必須なのか（本章の要点）

トラッカーには実際の代償がある：**状態がリポジトリを離れる**。 「セッションは起動時にファイルを読んで立ち上がり、コミット履歴でバックアップする」システムにとって、これは噛みつく：

- 新しいセッションは起動時に最新の状態を読めず、再び伝言頼みに逆戻りする；
- リポジトリのバックアップ（リモート HEAD の照合）は、トラッカー内の状態をカバーできない；
- トラッカーが一度止まったり放棄されたりすれば、歴史的な状態は丸ごと失われる。

解法はトラッカーを拒むことではなく、還流管を一本付けることである：

- トラッカーの操作には**ローカルにのみ接続する API クライアント**を使う（チケットを開く、コメントする、チケットを閉じる、エクスポートする）。クライアント自体はリポジトリに入れ、テストを通す；
- トラッカーの全状態を定期的に**スナップショットファイルとしてエクスポートし、リポジトリへコミットして戻す**（例：JSON/CSV＋人が読む要約）。スナップショットがすなわちバックアップであり、起動時の読み物である：セッションは起動時にスナップショットを読み、深い操作は API で行う；
- トラッカーの選定では**単一ファイル／軽量なローカルデプロイ**を優先する（コードホスティングとチケットを一体にした Gitea のようなオープンソースツール。ワークフローの深さがさらに要る場合は Redmine のようなもの）。整式が一台のマシンで再構築できることを保証する。

## 層分け：何がトラッカーに入り、何が入らないか

| 層 | 規模 | 担い手 |
|---|---|---|
| 機械規模：一括マイクロタスク、自動採点、親子派生 | 百～千 | 追記台帳（クレームボード）、プログラムが管理 |
| 人間規模：タスク、質問、決定、事故 | 十～百 | トラッカー、フィールドとワークフローが管理 |
| 不変の真源：原始の指示、文書、証拠 | — | git リポジトリ。チケットには番号とリンクだけを掛ける |

機械規模をトラッカーに詰め込むと、まずトラッカーが潰れる（ノイズ、一括操作、カスタム状態機械は、そのために設計されたものではない）。人間規模を表に残せば、漏れと忘れは解けない。層分けは、両方向の失敗をどちらも避ける。

## ワークフローに書き込まなければならない教訓：閉単の単点

トラッカーのデプロイが失敗する最もありふれた形は、誰もチケットを開かないことではなく、**チケットを閉じる権限が一人に集中している**ことである：その人が止まると、未閉のチケットが山積みになり、システム全体が放棄される。だからワークフローには少なくとも二つのルールが要る：

- 閉単の権限を単点にしない（審査者と調整者の双方が閉じられる。作者は依然として自分のものを閉じられない）；
- 期限を超えて動いていないチケットは、静かに横たわらせず、毎日の一ページ／日報へ自動で格上げする。

## 試点の規律

上線は採用ではない。近い将来の**照合日**を約定する：チケットごとにトラッカーと実際の仕事が一致しているか、毎日の一ページがクエリ／スナップショットから生成され始めているか、閉単が依然として単点でないかを照合する。照合に通らなければ、直すか表に戻し、その理由を変更記録に書く——ツールは結論と同じく、「使った後に否と言える」ことに耐えなければならない。
