# 02 · アーキテクチャ：役割、セッション、情報フロー

## 一セッション一名前

- 長期セッションは一つにつき一つのポスト、一つの固有の名前とする。名前がそのまま宛先になる：仕事の割当て、メッセージ、成果物の提出はすべて名前で指名する。
- 名前を共用すると、受信箱の奪い合い、カーソルの奪い合い、重複返信が起きる——これは実測された故障モードであり、潔癖ではない。
- 新しいセッションが作業を始める前に、名簿に一行登記する：名前／実行環境／役割／何を頼む相手か／状態。
- 一時的なサブエージェントはポストではない：出所を署名に付し（例：`メインセッション・サブエージェント`）、名簿に入らず、仕事の割当ても受けない。

## 役割リファレンス表

| 役割 | 職責 | やらないこと |
|---|---|---|
| 総責任者（受付口） | 仕事の割当て、受領の登記、唯一のタスク状態表の維持、リソース（枠／計算資源）のスケジューリング | 特定の研究ラインの長を兼任しない。探索の一歩ごとに承認しない |
| 研究責任者（ラインごとに一人） | そのラインの課題の仕様、事前予測、締めくくりページ | 自分の産出物を審査しない |
| 実行者／解題者 | 仕様に従って計算、リプレイ、集計、データ探索を行う | 仕様を変更しない。仕様に問題を見つけたら報告し、口径を勝手に変えない |
| ツール保守 | 公共ツール（チェッカー、台帳、スケジューリング）を作り保守する | 未審査のツールを判定者に使わない |
| 審査（少なくとも二人、相互に独立） | 問いへのブラインド読み戻し、コード監査、独立再計算、変異テスト | 作者の結論を先に読んでから判定しない。自分が審査した仕事の手戻りを引き受けない |
| データ／経路保守 | データの着地、完全性ゲート、暴露登記 | 研究判断には触れない |
| 統括 | 原話の登記、進捗ページ、対外報告 | 研究の仕事を割り当てない |
| 外部審査（任意） | 読み取り専用の審査、改善候補の提示 | 仕事を割り当てず、ファイルを変更しない。その産出物はすべて「候補、未検収」と表示する |

## 単一受付口

- プロジェクト全体でタスク状態表は一枚だけ、書き手も一人だけ（総責任者）。
- 提出フロー：成果物の冒頭に提出ブロックを書く → メッセージチャネルで受付口に通知する → 受付口が照合し、状態表に登記する。
- 「既読」≠「受領済み」。「受領済み」≠「結論が肯定的」。三つの状態は分けて記録する。
- 受付口は集約点であって承認点ではない：探索レベルの試行錯誤に段階的な承認は不要。ゲートを通るのは三種類の行為だけ——**発見の主張、証拠の格上げ、リソースの動員**である。

## 二ライン対照（任意、強く推奨）

- 同じリポジトリ、同じ台帳、二つの自律的な研究ライン（A ライン／B ライン）。探索の権限は同等とする。
- 両ラインの比較は、**同じ課題、同じリソース制約、同じ検収基準**で行わなければならない。一方に旧問題の修正、他方に新課題をやらせて強弱を比べるのは無効である。
- ライン間の相互チェックは事故ではなく特性である：一つのラインが他方のツールに変異テストを行い、暴露登記の誤りを探す。第三者が独立に再現して初めて数に入る。
- 両ラインが同じデータ群にアクセスするとき、検索と選択の履歴は**合算する**。別々の帳簿は許されない。

## 情報フロー

- **原話の真源**：提案者の原話の登記場所は一か所だけ。追記のみ、番号付き。他の文書は番号を引用し、言い換えを複写しない。
- **タスク状態の真源**：状態表の一か所だけ。チャット内の進捗発言は数に入らず、食い違えば表を正として遡って調べる。
- **メッセージチャネル**：日常の連絡は軽量なメッセージ／ブリッジで。例外（安全、決定、争議）だけ正式記録に格上げする。
- **毎日の一ページ**：ラインごとに毎日一ページ。冒頭で根本要求と照合し、本文には「今日どの判断が変わったか、どこで詰まっているか、次は何か」だけを書く。
- **プッシュ規律**：各ラウンドの終了時に成果をリモートバックアップへプッシュする。ローカル HEAD とリモートの不一致はバックアップ未完了とみなす。（これがなければ、外部の観察者にはいつまでも昨日の世界しか見えない。）

## 枠とスケジューリング

- モデルの枠、計算資源、審査の人力はすべて**スケジューリング可能なリソース**であり、状態表に書き込んで一元的に配分する：ある種類の枠が凍結されたら、全ラインを止めるのではなく、それに依存しない役割へ仕事を回す。
- 総責任者は**定時起床**制を採れる：起床のたびにまず読み取り専用のチェッカーを走らせる（受領漏れの成果物はないか、期限切れの申込はないか）、次に受信箱を読み、コミットを照合し、状態表を更新する。自動駆動がなければ、止まったセッションは止まったままである——だからチェッカーは「誰が、どれくらい詰まっているか」を一目で示せなければならない。
